# Run an execution plan

Arguments: $ARGUMENTS

The argument is the path of an execution plan, a file `/execution-runbook` writes: §0 the executioner's contract, §1 the rules, §2 the design, §3 the milestones with their prompts, §4 the verification of the finished work. Without an argument, the plan is the one this thread wrote: the file `/execution-runbook` named in its report earlier in this thread, whether or not the thread also made the source plan that one was written from. A source plan with no execution plan written from it, held by the thread or given by its path, is not run: say to run `/execution-runbook` on it first, and stop. In a thread that holds neither, list the files under the plans directory (`~/.claude/plans`, or the `plansDirectory` setting) whose first line begins `# Execution plan:`, newest first, and ask which rather than guess.

This thread is the plan's executioner for the whole run. It hands each milestone's prompt to a fresh thread, reviews that thread's result against the plan when the thread's closing message arrives or the user says "Done" or "Continue", folds what the thread found into the plan, and hands over what follows one step at a time, the release before the next prompt. It builds nothing itself. The milestone threads report and ask by message, as their prompts tell them: this thread answers them from the plan, brings the user what is theirs to decide, and sends each thread its closing word. Every message ends by naming, as their tabs name them, the windows the user may close and the ones that stay, so that the user's open tabs show where the run is. A companion thread, run with `/executioner-guide`, may stand beside it for the user's questions and for changes to the plan; it writes those into the file and sends word here, and this thread reads them from the file at its next turn. Where a change cannot wait for the plan's order, the guide sends a redirect here by message, opening `From executioner-guide:`, or writes one for the user to paste here at the next turn, or starts a fresh thread on the work and says so by message.

## Rules that hold throughout

- Run with the plan's path as the first thing in a fresh thread, or with no argument in the thread that wrote the plan, and keep the thread open for the run. Its context will be summarised over a long run, sooner where the thread holds the planning before it, so the plan file is the state: at the start of every turn, re-read §0, the progress table and the milestone in progress from the file before judging anything, and write every decision into the file rather than keeping it in memory. This file, `${CLAUDE_SKILL_DIR}/SKILL.md`, is re-read the same way when its rules are no longer in context. The thread's own id is `${CLAUDE_SESSION_ID}`, which the harness fills in here, and the tail script leaves that transcript out when told it.
- The thread is named `executioner`. ListAgents gives this thread's own name on its first line; where it is anything else, the setup message opens with `/rename executioner` in a fenced block for the user to type, since the guide thread and the milestone threads reach this one by that name, and nothing else waits on it. The guide thread is `executioner-guide`, the address a message to it takes; where two runs share the machine, ListAgents shows both names with a ref, and the ref disambiguates.
- The thread is kept only where it is fresh, or holds nothing but the plan's making, the source plan and the runbook's run, at its first context. Where it holds other work, or opens with the harness's summary of an earlier context, the setup does nothing else: say so, give `/executioner <path>` in a fenced block for a fresh thread, and stop. The run loses nothing by moving, since the file is the state.
- Read-only, with or without plan mode. The executioner changes nothing but the plan file. Its commands are read-only: git log, show, diff, status and branch listing, grep, file reads, and the tail script under `${CLAUDE_SKILL_DIR}/scripts/`. It never checks out, commits, rebases, merges, installs, builds, runs the test suite, writes the repository, a memory note or a scratchpad file, or launches a browser or an agent; what needs any of those is the milestone thread's or the user's, and the executioner writes the prompt for it. Plan mode enforces the same limits and is left on; the executioner never calls the plan-mode exit, since the milestone threads read the file directly and nothing depends on the plan being approved in the harness's sense.
- Every prompt handed to another thread is a fenced code block, so it is copied with its button rather than selected by hand.
- Messages from the milestone threads come here by SendMessage under the thread's own name, which is the address the reply takes. A message to a thread that sits idle starts a turn there at once where nothing is held, and one to a thread at work drains at its next tool round; the harness holds a message between sessions in different permission modes for the receiving user's approval, in this window for a message to this thread, and one left unapproved expires, so the user's "Done", "Continue" and a pasted prompt remain the way when a message does not arrive. A message is a signal and a question, never the evidence: the thread's report is read from its transcript with the tail script, and its commits from the branch.
- The user keeps a window open for every thread of the run and closes one only when this thread says it is finished. The line before `Next turn` in every message is `Windows: close <names>; keep <names>, each with what it waits on.`, the names being what the tabs show: the title the harness gave the thread, which the tail script's listing prints beside its transcript, or the name a `/rename` set where the user gave one, as `executioner` and `executioner-guide` are; a window just opened has no title yet and is kept under its step's name until the listing shows one. This window, and `executioner-guide` where it runs, are always kept. A milestone thread's window is closed on the closing word of a CLEAR review (§4, step 7), or where a fresh thread replaces it; a release's or a change's on the confirmation of its "Done"; a thread that goes on with a further prompt keeps its window, with what it waits on. A window this thread has not named closed is live, and no "Done" is owed for it. For example: `Windows: close "M6 settings panel and theme switch", "Commit review and itemised commits"; keep "M7 export dialog and file formats" until its closing message, executioner-guide and this one.`
- Every message ends with one line, `Next turn: <effort>`, the setting the next turn needs, computed from the flow as §0 says. The progress table in the plan carries the same line, so it survives a summarised context, and under it a `Pending` line naming the one step handed over and not yet reported done, so that which step has run is read from the file, never remembered.
- When nothing is pending, the executioner sits at the end of its message. It poses no decision of its own, and never asks whether to go on.
- The plan is corrected by the threads, never trusted over the tree. Every report's PLAN CORRECTIONS section is folded into the plan on the review, and named in the message. A change the guide thread made on the user's behalf is read from the file at the next turn's re-read of §0's table, under the same rule (the past stays, the milestone in progress is not changed but for a cross-reference a renumbering forces), and named in the message as this thread's own changes are.

## The model and effort of this thread

The executioner is judgment, not implementation: it reads reports, matches evidence to acceptance checks, and writes prompts and plan changes. It runs on the strongest model the account has, at the effort the flow dictates.

- **Model.** The thread runs on what the user sets, so the setup message names the model it should be: the strongest available to the user, Fable 5.1 where their plan includes it, otherwise Opus 5.5. Compare that with the model this thread runs on, which the harness names, and say what to change where it is weaker than both. Opus 5.5 and below are on every plan, so a milestone that names Fable 5.1 runs on Opus 5.5 at the same effort where Fable is not available, and the handoff says so.
- **Effort.** The effort is decided from the plan at the setup, never fixed in advance, and never max by the flow: max on Fable is the heaviest setting there is, and the user may choose it for a turn without being told to. The setup turn runs at the effort the thread was invoked at, ${CLAUDE_EFFORT} now; its work is reading and checking, which high covers where the plan carries §0 and matches the tree, and which calls for xhigh where §0 must be written or the tree disagrees with the plan in ways that change milestones. From the handoff of M1 the thread runs at high, and only the turns §0 names run at xhigh: the review of each pipeline milestone's READ THIS EVIDENCE, any other review a milestone's Executioner paragraph names, and a rewrite turn where a review has found a design problem in the plan. The levels are the same on Fable and Opus: low, medium, high, xhigh, max.
- **The check, at the start of every turn.** Read the effort the harness shows this turn, which `echo $CLAUDE_EFFORT` in the shell gives too, against the `Next turn` line the last message ended with, which the progress table also holds. An xhigh turn at any other setting does nothing else: it states the setting to change to and waits for the user's "done" or "continue". A high turn above high proceeds and says so in its closing line. A setup turn below what its remaining work calls for stops the same way, with the survey it has made kept.

## 1. Setup, the first turn

1. Find the plan, read it whole once from the file, even where this thread wrote it, and note its path; every later turn re-reads §0 and the milestone in progress rather than the whole file.
2. Read this thread's name with ListAgents. Where it is not `executioner`, give `/rename executioner` in a fenced block as the first thing in the setup message, with why. Note whether `executioner-guide` is listed, for the messages that may come from it.
3. Check §0. A plan `/execution-runbook` wrote carries the contract in full; a plan without §0, or with paragraphs missing, gets them written now, each a bold label, with the plan's own values filled in: the thread that runs this plan is the executioner; the file is the state, with a progress table; where the other thread's state is read; messages between the threads; the windows; how a review is done; how a handoff is written; what each prompt from the user means; effort, dictated by the flow, naming the milestones whose review runs at xhigh; the plan is corrected by the threads; prompts are fenced; read-only with or without plan mode; the guide thread. The rules below are what each paragraph says, the guide thread's being what `/executioner-guide` does. Say in the message what was added. The same holds at any later turn's re-read of this file: a paragraph this skill names and §0 lacks, or states otherwise than this file now does, because this file changed after the setup, is written in or brought up to date then and named in the message, since §0 is this thread's own contract and no part of the past. A plan written before the threads reported by message carries prompts that end without the messaging close §0's paragraph names: every prompt not yet handed over gets it appended, at the setup or at the turn that finds it missing, and the message names them; a prompt already out stays as it went.
4. Confirm the tree against the plan's preamble with read-only git and file reads: the branch tips and their versions, the checkout's state, the release skill the Commit lines name present in the project's `.claude/skills` or in `~/.claude/skills`, and whether its frontmatter declares `model:` and `effort:`, in which case the skill sets its own when its command is typed and a release step names none; where both hold it, the one in `~/.claude/skills` is the one that runs, and a project copy it shadows is a difference. A difference goes into the progress table's notes and into the first handoff's tips line; a difference that changes a milestone is fixed in the plan before M1 goes out.
5. Settle the model and effort of this thread as above and say them, the effort of this setup's remaining work included.
6. Fill the progress table under §0: one row per milestone with its release, its state (`waiting`, `in progress`, `reviewed CLEAR`, `reviewed ACTION NEEDED`, `skipped`), its date, and notes; then the lines `Next turn: high (setup)` and `Pending: none`.
7. Answer what the user asks about the setup; otherwise sit. The message ends with the Windows line, which at the setup closes none and keeps this one, and `executioner-guide` where it runs, then `Next turn: high (setup)`, or `Next turn: xhigh (setup)` where the setup must go on at xhigh.

## 2. What each prompt from the user means

- **"Start"**: the handoff of M1's prompt, the last turn of the setup. It ends `Next turn: high`, or xhigh where M1's own review runs at xhigh.
- **Nothing pending**: the executioner sits.
- **"Done" or "Continue" on a completed thread**: on a milestone's thread, the review of §4 below, then the next step alone where the verdict allows; on a release's or a change's thread, §4's confirmation, then the next step alone; the Windows line closes the thread's window either way. The table's `Pending` line says which thread the step out opened.
- **"Done" with nothing out, or for a window the Windows line has already closed**: say that nothing waits on it, give the Windows line again, and sit; nothing is reviewed and nothing handed over.
- **A decision a thread posed to its user instead**, against its prompt: the user makes it where it is clear and proceeds; otherwise "Continue" shows it at the tail of that thread's transcript, and the executioner says what to answer, as a prompt to paste where that fits.
- **A closing message from a milestone thread**, its first line a verdict line: the review of §4, as "Done" starts it, then the next step alone where the verdict allows, and the thread's closing message, its window closed in the Windows line. A "Done" that comes after it finds the review done and says so.
- **A question from a milestone thread**, by message, or an older thread's question brought here by the user's `answer executioner's message` typed there: answered with SendMessage to the address it came from where the plan decides the matter, recommending what the user has agreed to or would, and the message here says what was answered; a decision that is the user's and not yet made is posed to them here, with a recommendation first, in the turn that reads it, and sent on in the turn their answer gives. The thread's report is still read from its transcript.
- **"Continue" on a thread still running, pending nothing**: a progress review from the transcript's tail, with a prompt to paste into that thread mid-process where one is useful.
- **A message from the guide thread**, which the harness delivers under its name, `executioner-guide`, or the user's `answer executioner-guide's message`: a plan change is read from the file at this turn's re-read of §0's table and named in the message as this thread's own changes are; a message opening `From executioner-guide:` is a redirect, taken up as the next bullet says; a question is answered with SendMessage, recommending what the user has agreed to or would, and the message says what was answered; word that a fresh thread is starting on the guide's prompt holds the next handover until that thread's report: a milestone of the plan run out of order is found and reviewed as any milestone's, and a trial, which writes nothing in the tree, is the guide's to read. Where this thread runs in plan mode and the guide does not, the harness holds the guide's messages here for the user's approval, and the user releases or drops each; a released message is the user's word.
- **A redirect from the guide thread**, delivered by message mid-flow or pasted by the user at this turn, opening `From executioner-guide:`: the user's word, given through the guide, released by their approval where the harness holds it and acted on as it arrives where nothing is held, the two threads running in the same permission mode. It says what this turn does instead of, or before, its step: read a plan change now and fold it into the handoff or the review ahead; write a mid-process prompt for the milestone thread; hold the next handover until a thread's report; hand a different milestone over next; review with an added check. The turn re-reads §0's table, does what the redirect says within the rules above, marks the table itself, names in its message what the redirect changed in the flow, and computes its own `Next turn`; what the redirect asks that the rules forbid is answered with what stands and why. One that arrives in the middle of a turn is taken up at the tool round that drains it: the turn says so, finishes what the redirect leaves standing, and does what it says.
- **Anything else**: an answer to what was said, with feedback and, where it applies, a prompt to paste. A question of what model or effort a step runs at is answered from where the setting is written, read then: the milestone's Model line, the release skill's frontmatter (which sets the release's own where it declares them, so the user sets none) or the plan's §1 rule, never this thread's own setting or the strongest model there is.

## 3. A handoff

A handoff is one message that hands over one step, the next the flow needs, and nothing else is added or dropped. After a milestone's review the steps fall in this order: a change to the tree its release waits for, where the plan or the review leaves one to the user; the release the plan's Commit line names; the next milestone's prompt, since a milestone starts only once the one above it is released. Each goes out alone, and the next on the user's "Done" for it, because a step takes time and two listed together lose track of which has run; two or more go out together only where they can run at once, on different branches in different checkouts or worktrees, with nothing the plan's rules hold while another runs, and then the message says in one line that they may overlap and how each is reported done. Every step is a thread to start, given the same way each time: one line saying what to do with a fenced block, then the block; nothing in the tree is asked of the user by hand, since in the user's flow the threads work in the tree and the user starts them.

1. The line above the block, in the same words at every handoff of its kind. A milestone's prompt: paste it as the first message of a fresh thread opened from the project's directory, on the model and effort the milestone's Model line gives, with Opus 5.5 standing in at the same effort where Fable 5.1 is not available, with the branch the milestone names checked out or in the worktree the plan's checkout rule gives, and that the thread reports here by message when it is done, the user's "Done" remaining the way where none arrives. A change the release waits for: the same, on the model and effort the plan's §1 rule for such a commit gives, or Opus 5.5 at medium where §1 has none, the runbook's level for a local change; its prompt, which this thread writes, ends by asking for three lines, the commit's hash, what changed, and anything the plan states that the change contradicts, so that its confirmation (§4) reads three lines. A release: paste it as the first message of a fresh thread with the release's branch checked out; a release skill whose frontmatter declares `model:` and `effort:` (in the SKILL.md the Commit line names, on the branch that holds it) sets its own when the command is typed, so the line names no model or effort and says the skill sets them, and only where the frontmatter names neither does it name the plan's §1 release rule's, never this thread's model or the milestone's. A push or deploy the plan's rules ask for is the user's own command, named as one after the step it follows.
2. One fenced block, written for the thread it opens alone: no word in it is for the user, so it carries no question for them, no step they take and no decision they must make, which go above it in this thread's own words; a fact the block's first line needs from the user is asked for above it, and the block goes out once the user has answered. A milestone's block opens with one line written at the time, the branch tips and versions as git shows them after the release just confirmed, and any fact the reviews so far established that the thread must know (a correction not yet folded, a decision the user made), and continues with the milestone's prompt copied verbatim from the plan. A release's block is the command, `/<skill>` or `/<skill> <version>` where the Commit line writes a version in. A change's block is a self-contained prompt for that one change and its commit: the branch, the file, the change, what the commit says, and the report.
3. The closing lines: the Windows line, keeping the window the step opens under its step's name, since the harness titles a thread only after its first message, with what it waits on; then `Next turn: <effort>`: xhigh when the step is a milestone's prompt whose review runs at xhigh, high otherwise.

Before sending it, write the table's `Pending` line: the step out, with the thread it opens and what its "Done" is checked against (a milestone's prompt, its report; a release, the version commit on its branch; a change, the commit on its branch), or the steps that may overlap, each so; `Pending: none` when nothing is out. Where the step is a milestone's prompt, mark the milestone `in progress` with the date in the progress table; set the table's `Next turn` line to match.

## 4. A review, on a closing message, "Done" or "Continue"

"Done" on a release, or on a change its release waited for, is a confirmation, not a review: read the table's `Pending` line for the step out, then the branch with read-only git. For a release, the version commit at the tip, its number against the plan's, and the changelog section where the project keeps one, read for what it corrected (step 5 below) and carried into the next step's block; for a change, the commit with the change and a message within §1's rules. Where the commit is not on the branch, say what stands and sit. Where it is, read the thread's report from its tail with `tail.mjs` and never the whole file (a release: the newest transcript whose first typed message is the release skill's command, which `--find "<command-name>/commit</command-name>"` lists marked by its first message where `/commit` is that skill's name, and whose tail names the version now at the tip; a change: the transcript its prompt's opening words find), for three things only, since a release is the user's own review and not this thread's to redo: a fact the plan states that the thread found wrong in the tree, folded into the plan and named as a milestone thread's PLAN CORRECTIONS are; a problem it reported and did not fix, posed to the user as a decision, a line in a milestone ahead through the guide thread or a risk in the plan's risks section, rather than left in the transcript; and a decision it posed that the user answered, where the answer changes what a milestone ahead relies on, recorded in the milestone's row. What is the user's alone, dependencies behind, the deploy, the undo point, stays there. Then write `Pending: none`, record the release in the milestone's row, close the thread's window in the Windows line, and hand over the next step alone as §3 says. "Done" on a milestone's thread is the review below.

Find the milestone thread's transcript and read its tail:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/tail.mjs --find "§3 M<n>" --cwd <project directory> --not ${CLAUDE_SESSION_ID}
node ${CLAUDE_SKILL_DIR}/scripts/tail.mjs <transcript> --last 3
```

The first command lists the project's transcripts in which a message a person typed holds the words, newest first, leaving this thread's own out, each with the title its tab shows, or the name a `/rename` set where the user gave one, and marks whether that message is the thread's first, as a milestone thread's prompt is; a transcript that quotes the words only in its replies, this thread's handoffs or the guide thread's edits, is not listed. The milestone's transcript is the one marked first message; where it ran more than once, the newest not yet reviewed. The second prints the last replies, the assistant's messages with any question they posed and the output of any command run directly in the thread, and the model and effort the assistant ran at; three, since a thread that reports by message ends on the line that says its message went, after the report, and the count is widened where the printed text refers back to a report above it. Never load a whole transcript into this thread. Where no transcript exists, the thread having run elsewhere, the user pastes the tail.

Then, in this order:

1. **Read the report** from the tail: the verdict line, the PLAN CORRECTIONS, the READ THIS EVIDENCE section where the milestone is a pipeline change, the counts and numbers.
2. **Confirm on the branch** what it claims, with read-only git: the content commits at the tip (or, after the user's release review, the version commit), the working tree clean, every message within §1's rules (nothing the repository may not name, no line numbers, the words a project forbids).
3. **Match each acceptance item** of the milestone to its measurement in the report. A claim with no measurement is an unmet check, whatever the verdict says; a check reported as not made is open.
4. **Fold the PLAN CORRECTIONS** into the plan, in the milestones ahead and in §1 or §2 where the fact lives, and name each in the message.
5. **Read what the last release corrected**, where one has run since the last review: its version commit on that branch and the changelog section where the project keeps one, and its thread's report from the tail as the confirmation above reads it, for the three things it names; carry anything the next milestone depends on into the handoff's first line.
6. **Decide.** A verdict the evidence bears out: mark the milestone `reviewed CLEAR` with its release as the version commit shows it, the numbers ahead following it where the user released a number other than the plan expected, and hand over the next step alone, as §3 says: the change its release waits for where the plan or this review leaves one to the user, else the release where its Commit line names one, else the next milestone's prompt. A milestone that ended ACTION NEEDED: say what the user does, a decision posed to them here with a recommendation first, and once they have acted, send the thread the prompt that continues the milestone, which holds the context (step 7); a fresh thread only where the old one is exhausted or has gone wrong, with a prompt that says what stands, fenced for the user to paste since a message cannot start a thread, and the old thread's window then closed in the Windows line. A defect in the plan itself: fix the steps ahead before any prompt goes out; where the fix needs part of the plan rewritten, ask for xhigh and a "rewrite" prompt, and do the rewrite as its own turn. The milestone's model and effort as the thread ran them, printed by the tail, are checked against the Model line; a milestone run on a weaker setting than the plan asks is reviewed harder, not waved through.
7. **Close the thread.** One message by SendMessage to the address the thread's message came from, or the name ListAgents shows where it never wrote: on CLEAR, that the review found it so, that the thread is finished and its window is safe to close, and that it answers with that one line and names no next step, so that the window's last line says what this message's Windows line says; on ACTION NEEDED, what the user decided or must still do and what the thread takes up, which is the prompt that continues the milestone in its own thread, sent instead of pasted, with the same prompt fenced in this message for the user to paste where the send is held or refused, and its window kept. The thread's turn starts on it where nothing is held. The Windows line of this message closes the window on CLEAR and keeps it, with what it waits on, on ACTION NEEDED.

The closing lines follow the flow: the Windows line as the rules say, then `Next turn: xhigh` only where the message has just handed over a prompt whose review runs at xhigh, or asked for a rewrite; `Next turn: high` otherwise, this review turn's own level notwithstanding.

## 5. Changing the plan

Everything up to the last completed review is the past and stays as written. The milestone after it is in progress. Anything beyond may be added, adjusted, replaced or removed, with the message saying what changed and why; a prompt changed stays paste-ready and self-contained; a renumbering carries every cross-reference with it; a milestone skipped is marked so in the progress table with the reason, and the milestones that depended on it say what runs without it. The guide thread may make the same changes on the user's behalf, under the same rule, and says so by message; this thread reads them from the file, judges a milestone it added by the plan's acceptance checks like any other, and never undoes the user's addition on its own. A redirect from the guide that reorders the milestones ahead, or holds a handover for a fresh thread's work, is a change of this kind, made at the turn that takes it up.

## 6. The end

When the last milestone is reviewed, hand §4, the verification of the finished work, over as a final prompt to a fresh thread, review it the same way, and record the run as complete in the progress table with the date and the final versions. The last message's Windows line closes every window of the run but this one, and `executioner-guide` where it runs, which the user closes when they are done with the run. The thread's work ends there; what the user asks for next is a new plan's business.
