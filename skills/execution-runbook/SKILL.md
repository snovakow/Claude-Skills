# Write an execution plan

Arguments: $ARGUMENTS

The arguments are an optional version, written like `7.1.0`, and an optional path to the source plan: the plan laid out beforehand that this run turns into an execution plan. The version is the number the execution plan's first release carries, where the project keeps version commits, and is needed only where that number is not the release skill's own bump (step 6). Without a path, the source plan is this thread's own: the plan the thread made, in the plan file the harness named for it or in its messages, or a plan pasted after the command. A thread that holds none, the command being its first message with nothing after it, is asked for the path, and the skill stops there.

Read the source plan whole before the survey. Its decisions are the user's and stand, going into §1 as dated decisions without being asked again; its parts and their order are where §3 starts; its claims about the code are readings to check against the tree, never facts.

The execution plan, "the plan" from here on, is a markdown file that other threads execute one milestone at a time, each in a fresh thread with the milestone's prompt as its first message, while a manager thread, the executioner, hands the prompts over and reviews the results against the plan. This skill writes the plan; `/executioner` runs it, and `/executioner-guide` answers for it and changes it while it runs. Everything a milestone thread needs is in the file: the rules, the design, its own section and its prompt. Nothing travels by memory.

## Rules that hold throughout

- Run it in the thread that made the source plan, with no path, or as the first message of a fresh thread, with the source plan's path; in plan mode where the plan can be the thread's own plan file, as *Where the plan goes* says. Where the thread made the source plan, what its discussion decided goes into the plan as dated decisions beside the source plan's own.
- The thread is kept only where everything it holds is the source plan's making, at its first context. Where it holds other work, or opens with the harness's summary of an earlier context, say so before the survey and stop, giving the command for a fresh thread in a fenced block: `/execution-runbook <the source plan's path>`, the version first where one was given, or the command with the plan pasted after it where the plan is not a file; and list any decision the thread made that the source plan does not carry, for the user to write into it first.
- Change nothing in the repository: no checkout, no commit, no install, no build, no edit to a tracked file. Read-only git, file reads, searches and subagents that search are the tools. The one thing written is the plan file. The test suite may be run once for its count where the project does not record it, and only when running it writes nothing into the tree.
- Treat every fact as a reading of the tree at a named commit, dated. The plan says so, and the threads verify what they rely on.
- The plan names the person by the first name `git config user.name` gives, or "the user": a prompt is read by a thread, so "you" in one means the thread.
- Keep the plan outside the repository, under the plans directory (`~/.claude/plans`, or the `plansDirectory` setting), so no thread can commit it and every thread can read it.

## Where the plan goes

- In plan mode, the plan file is the one the harness names for the thread, and the only file plan mode writes. Write there. Where that file holds the source plan, stop before the survey and say so, with the two ways on: plan mode off in this thread, after which the plan goes beside the source plan at the path below; or `/execution-runbook <the source plan's path>` as the first message of a fresh thread in plan mode, where the plan is that thread's own file.
- Otherwise, write to `<plans directory>/<repository folder name>-<topic>/execution-plan.md`, the topic a few kebab-case words for what is built, the folder made with `mkdir -p`. That folder is under `~/.claude`, a protected one: the default permission mode asks before the write, and auto mode's classifier judges it. The source plan is never overwritten.

Every prompt in the plan opens with "Read `<that path>` §1 …", so settle the path before writing a prompt.

## 1. Survey

Before any subagent runs, take the facts that frame everything, each from the tree or git, never from memory:

- the branches the work lands on, their tips and versions, whether the checkout is clean, and what `main` points at
- the release skill, if one is installed: `.claude/skills/commit/SKILL.md` and any sibling such as `commit-editor`, in the project or under `~/.claude/skills`. Where both hold a skill of the same name, the one under `~/.claude/skills` runs and the project's never does: read the one that runs, and say that the project's is shadowed. Read whether its frontmatter declares `model:` and `effort:`, which then set the release's own when its command is typed, and its settings block: the protected branches, the version shape and whether runs end with a version commit, the checks it runs, the docs it maintains, the names it never mentions, and whether it must be run in a fresh thread. These become rules of §1 and the Commit lines of §3.
- the skills that will run the plan, if installed: `.claude/skills/executioner` and `.claude/skills/executioner-guide`, in the project or under `~/.claude/skills`, as links or copies, since the next step the report gives in step 9 depends on which are present
- the project's own instructions: `CLAUDE.md`, the docs folder, and the memory notes in the project's memory index that bear on the source plan. Rules that bind the work are restated in the plan, each once, so that no thread needs anything but the plan and the repository.
- the test runner, the current test count where the project records it (a changelog section, a release note; otherwise one run of the suite), and the build command with its cautions
- the size of what is replaced or extended: line counts of the modules involved, where they are imported, the one thing that uses them today
- the precedent: the commit that last added something of the same shape (a new kind, a new pass, a new window), by hash and file count, since its touched files are the seam list a milestone copies

Keep each fact with its source: the commit, the file, the function.

## 2. Size the job

This thread runs at ${CLAUDE_EFFORT}. The plan's judgments are what the whole execution runs on, so the thread runs on the strongest model the account has, Fable 5.1 where the user's plan includes it, otherwise Opus 5.5, and at the effort the source plan's size calls for, decided now from the survey rather than fixed in advance:

- **high**: one area of the code on one branch, a few milestones, no pipeline change.
- **xhigh**: several areas or two branches, a pipeline change, a removal across many files, or about eight milestones or more.
- **max** is never called for: the stress-test of step 8 runs at xhigh in its own context whatever this thread runs at, and max on Fable is the heaviest setting there is. The user may still choose it.

Say the size and the setting it calls for in the first message, beside the setting the thread has. Where the thread runs below it, stop there: say what to set, and that "continue" resumes from step 3 with the survey kept. Where it runs above it, proceed and say so.

## 3. Explore

Launch one Explore subagent per area the source plan touches, in parallel, breadth "very thorough", each briefed with the repository's layout and asked for the seams by name: the files and functions a change goes through, the precedent's touched files, the tests beside them, the conventions a module follows, and what the source plan's words map to in the code. Gather the cheap facts yourself while they run. Where a design choice is risky, have a Plan subagent check it against the code before it is written in. Trust nothing from the source plan or a note over the tree: a claim that matters is read in the source.

## 4. Decide

Collect every choice the source plan leaves open that would change the plan: a mode kept or dropped, a port versus an in-place change, a layout model, and, where the project keeps version commits, whether each release line takes the release skill's own bump or a jump, the bump recommended, except the line whose first number the arguments give; a line with no version commit yet has no bump, so its first number is asked outright. Add each decision of the source plan that the tree contradicts, with what the tree shows; the rest of its decisions are not asked again. Ask them all in one AskUserQuestion, the recommended answer first with its trade-off, before writing. The answers go into §1 as dated decisions every milestone follows.

## 5. The shape of the plan

Write it in this order. Headings are the sections; bold run-in labels are the paragraphs. The two plans this shape was taken from ran fourteen and fifteen milestones; a smaller source plan makes fewer.

**Title and preamble.** `# Execution plan: <the thing>`, then one paragraph: what it is in a sentence, the date and the tip it was read from, the source plan by its path where it is a file, the decisions folded in, and "Milestones M1–M<n> run one per fresh thread in file order".

**§0. The executioner thread.** The contract of the thread that runs the plan, written so that the thread can re-read it from the file after its own context has been summarised. Its paragraphs, each a bold label:

- *The thread that runs this plan is the executioner.* It hands each milestone's prompt to a fresh thread, reviews that thread's result on the user's "Done" or "Continue", says how to proceed one step at a time, and may change this file: everything up to the last completed review is the past and stays as written; the step after the last completed review is in progress; anything beyond it may be added, adjusted, replaced or removed, and the executioner says in its message what it changed.
- *The file is the state.* At the start of every turn the executioner re-reads §0, the progress table and the milestone in progress before judging anything, and writes what it decides into the file. A progress table follows this paragraph: one row per milestone with its release, its state (waiting, in progress, reviewed CLEAR, reviewed ACTION NEEDED, skipped) and the date, and two last lines, `Next turn: <effort>` and `Pending: <the one step handed over and not yet reported done, with what its "Done" is checked against, or none>`.
- *Where the other thread's state is read.* The milestone thread's transcript is the `.jsonl` under the project's folder in `~/.claude/projects/` whose first typed message holds the milestone prompt's opening words, as the executioner skill's `tail.mjs` lists and marks it, never the executioner's own nor one that only quotes the words in its replies, the newest where a milestone ran more than once; its tail is read with the same script, never by loading the whole file. Where no transcript exists, the user pastes the tail.
- *How a review is done*, in order: read the report from the tail; confirm on the branch what it claims with read-only git (the content commits at the tip, the tree clean, every message within the rules); take each acceptance item of the milestone and find its measurement in the report, a claim with no measurement being an unmet check whatever the verdict says; fold the report's PLAN CORRECTIONS into this file and name them; where a release has run since the last review, read its version commit and changelog section for what it corrected, and its thread's report as the confirmation below reads it, and carry what the next milestone depends on into its handoff; then decide. A verdict the evidence bears out hands over the next step alone: a change the release waits for where one is left to the user, else the release, else the next milestone's prompt, each later one on the "Done" that confirms the one before it; a milestone that ended ACTION NEEDED continues in its own thread with a prompt the executioner writes once the user has acted, and a fresh thread is started only where the old one is exhausted or has gone wrong; a defect in the plan is fixed in the steps ahead before any prompt goes out.
- *How a handoff is written.* A handoff hands over one step, the next the flow needs: after a milestone's review, a change to the tree its release waits for where this file or the review leaves one to the user, then the release its Commit line names, then the next milestone's prompt, each alone and the next on the user's "Done" for it, since a step takes time and two listed together lose track of which has run, and since a milestone starts only once the one above it is released; two or more go together only where they can run at once, on different branches in different checkouts or worktrees with nothing §1 holds while another runs, the message then saying in one line that they may overlap and how each is reported done. Every step is a thread to start, given the same way each time: one line saying what to do with a fenced block, then the block; nothing in the tree is asked of the user by hand. The line: for a milestone's prompt, paste it as the first message of a fresh thread opened from the project's directory, on the model and effort the milestone's Model line gives, with Opus 5.5 standing in at the same effort where Fable 5.1 is not available, with the milestone's branch checked out or in the worktree §1's checkout rule gives; for a change the release waits for, the same on the model and effort §1's rule for such a commit gives, or Opus 5.5 at medium where §1 has none, its prompt ending with the request for the three lines §1's release rule names; for a release, the same with the release's branch checked out, naming no model or effort where the release skill's frontmatter sets its own, and §1's release rule's where it names neither; a push or deploy §1 asks for is the user's own command, named as one after the step it follows. The block is written for the thread it opens alone and carries no word for the user, no question for them, no step they take and no decision they must make, those going above the block in the executioner's own words, and a fact the block's first line needs from the user being asked for above it, the block going out once the user has answered: a milestone's block opens with one line the executioner writes at the time, the branch tips and versions as git shows them and any fact the reviews so far established that the thread must know, and continues with the milestone's prompt copied from this file verbatim; a release's block is the command, `/<skill>` or `/<skill> <version>` as the Commit line says; a change's block is a self-contained prompt for that one change and its commit. Before the handoff goes out, the table's `Pending` line names the step out and what its "Done" is checked against (a milestone's prompt, its report; a release, the version commit on its branch; a change, the commit), or the steps that may overlap; a milestone's prompt marks its row `in progress` with the date. Nothing else is added or dropped.
- *What each prompt from the user means.* "Start": the handoff of M1's prompt, the last turn of the setup. Nothing pending: the executioner sits and poses no decision of its own. "Done" or "Continue" on a completed thread: on a milestone's thread, the review above, then the next step alone where the verdict allows; on a release's or a change's thread, a confirmation with read-only git (the version commit on its branch and its changelog section, read for what it corrected; the commit with the change), then the thread's report read from its tail with the tail script, never the whole file (a release: the newest transcript whose first typed message is the release skill's command, which `--find "<command-name>/commit</command-name>"` lists where `/commit` is its name, and whose tail names the version now at the tip; a change: the transcript its prompt's opening words find), for three things only, since a release is the user's own review and not the executioner's to redo: a fact this file states that the thread found wrong in the tree, folded and named as a milestone thread's PLAN CORRECTIONS are; a problem it reported and did not fix, posed to the user as a decision, a line in a milestone ahead through the guide thread or a risk in §6, rather than left in the transcript; and a decision it posed that the user answered, where the answer changes what a milestone ahead relies on, recorded in the row; what is the user's alone (dependencies behind, the deploy, the undo point) stays there; then `Pending: none` written and the next step alone. A decision posed by the other thread: the user makes it where it is clear; otherwise "Continue" shows it at the tail and the executioner says what to answer, or the user types `answer executioner's message` in that thread, its question arrives here by message, and the executioner answers with SendMessage, recommending what the user has agreed to or would. "Continue" on a thread still running: a progress review, with a prompt to paste into that thread mid-process where one is useful. A redirect from the guide thread, delivered by message mid-flow or pasted by the user at the turn, opening `From executioner-guide:`: the user's word, given through the guide and released by their approval where the harness holds it, saying what the turn does instead of or before its step; the turn does it within these rules, marks the table itself and computes its own `Next turn`. Anything else: an answer to what was said, with a prompt to paste where it applies, and a question of what model or effort a step runs at answered from where the setting is written, the Model line, the release skill's frontmatter, which sets the release's own where it declares them, or §1's rule, never from the executioner's own setting.
- *Effort, dictated by the flow.* The setup, every turn before M1's prompt is handed over, runs at high, or at xhigh where this file lacked §0 or the tree disagreed with it, and those messages end `Next turn: high (setup)` or `Next turn: xhigh (setup)`; max is never dictated. From the handoff of M1 the executioner runs at high, and exactly the turns this file names run at xhigh: the review of each pipeline milestone's READ THIS EVIDENCE, and any other review the milestones' Executioner paragraphs name. One more is conditional: where a review finds a design problem that needs part of this plan rewritten, the review turn asks for xhigh and a "rewrite" prompt, and the rewrite is its own turn. Every message of the executioner ends with one line, `Next turn: high` or `Next turn: xhigh`, computed from the flow: xhigh only where the message has just handed over a prompt whose review runs at xhigh, or asked for a rewrite; high otherwise, the review turns included, since the message that reviews one milestone hands over the step that follows it, a release or the next prompt. At the start of every turn the executioner reads the effort the harness shows it against that line: an xhigh turn at any other setting does nothing else, states the setting to change to, and waits for the user's "done" or "continue"; a high turn above high proceeds and says so in its closing line.
- *The plan is corrected by the threads, never trusted over the tree.* Each report carries a PLAN CORRECTIONS section; the executioner folds every correction in on the review, so the next thread reads facts the tree bears out.
- *Prompts.* Every prompt handed to another thread, in this file or in a message, is a fenced code block, so it is copied with its button rather than selected by hand.
- *Read-only, with or without plan mode.* The executioner changes nothing but this file. Its commands are read-only: git log, show, diff, status and branch listing, grep, file reads, and its skill's tail script; it never checks out, commits, rebases, merges, installs, builds, runs the test suite, writes the repository, a memory note or a scratchpad file, or launches a browser or an agent; what needs any of those is the milestone thread's or the user's, and the executioner writes the prompt for it. Plan mode enforces the same limits and is left on; the executioner never calls the plan-mode exit. Where plan mode is off, this paragraph stands on its own.
- *The guide thread.* A companion thread run with `/executioner-guide`, named `executioner-guide`, is where the user asks about this plan and has it expanded or changed while the run goes on. It writes a change into this file under the same rule, the past unchanged and the milestone in progress untouched but for a cross-reference a renumbering forces, in the plan's own shape with every cross-reference carried, adds the progress row for a milestone it adds, marked waiting and naming the user's request, itself and the decision, and tells the executioner by message, which reads the change from this file at its next turn and names it. It marks no milestone's state, restates no step, and hands no milestone over in the executioner's place; where a change cannot wait for the plan's order, it sends the executioner a redirect by message, opening `From executioner-guide:`, which the executioner follows as the user's word once their approval releases it where the harness holds it, or writes the same for the user to paste at the executioner's next turn, or the first message of a fresh thread, a trial that writes nothing in the tree or a milestone of this plan run out of order, told here by message, whose work holds the next handover and whose report the executioner reviews where it is a milestone's; a fix goes into this file as a milestone first.

**§1. Context.**

- *What is being built.* The thing in a paragraph: what goes, what comes, what it reaches, in the project's own terms.
- *Decisions*, dated and attributed, which every milestone follows: the source plan's, those of the discussion that made it where this thread holds it, and the answers from step 4.
- *Inspiration, not source*, where the source plan names references: what they are the reference for and what is never copied from them, and the idiom everything is written in.
- *Rules that bind every milestone*, from the project's own instructions, each restated once: where work lands (branches, the worktree rule when the checkout is busy, how one branch rebases onto another); the release rule (a milestone is one or a few ordinary content commits on its branch; the release skill, run by the user as the first thing in a fresh thread, on the model and effort its frontmatter sets itself where it declares them, said here once so that no release step restates them, writes the version and the changelog section; a small commit of the user's own that a release waits for is a fresh thread too, on the model and effort stated here, Opus 5.5 at medium unless the project says otherwise, whose prompt the executioner writes and ends by asking for three lines, the commit's hash, what changed, and anything this plan states that the change contradicts, which its confirmation reads; the version scheme; what a commit message must carry for the changelog); what must never appear in the repository; comment and doc conventions; the compatibility rule (what an older document or input is owed, and what a fix reaching every launch must say); what must never be edited (another repository, existing test data); the test command and the count at the tip, the build command and its cautions, module boundaries; the domain's invariants (the rules a wrong change breaks silently); and this one, verbatim in spirit: **the plan binds on decisions and acceptance, not on its code facts**: every seam, name and behaviour claim is a reading of the tree at the named tip, made before the milestones ahead moved it; a thread verifies each claim it relies on against the tree it works in, follows the tree where the two differ, and reports every difference; an acceptance check is a measurement the thread makes, never the plan's expectation restated, and a check the thread cannot make is reported as not made.
- *How every milestone thread ends.* The last line of the report is one of two verdicts, on its own line: `CLEAR: commit made on <branch>; run /commit (or the project's release skill, with the version written in only where this milestone's Commit line writes one), then start M<n+1>.`, used only when every acceptance check passed, the checks are green and the live evidence shows no unexplained difference; or `ACTION NEEDED: <what the user must do or decide, in one or two sentences>.`, used when a check failed, a difference is unexplained, a device check is required before the commit is safe, or a decision in the milestone is the user's. The thread does not commit on an ACTION NEEDED unless the commit is complete and only the outside check remains, and says which. Anything short of a passed check is ACTION NEEDED, never CLEAR with a caveat. The report ends in a fixed order: a section headed PLAN CORRECTIONS (each place the plan's facts differed from the tree: the file, the function or constant, what the plan said, what is true; or the word "none"), then, for the pipeline milestones alone, a section headed READ THIS EVIDENCE naming the pairs and numbers the user reads personally, then the verdict line.
- *The live harness.* How a thread proves a change live in this project: how the thing is served and driven, from which tree, on which ports and never through the user's own; what counts as evidence (a screenshot's pixel or mean colour, a value sampled per frame, a ratio against the same harness on the same frames); how a before/after pair is made (a worktree at the old tip beside the new one); what cannot be driven from the harness and is the user's to check on a device.

**§2. The design in one place.** What every milestone builds toward: the document or data shape, the behaviour, the rendering or runtime path, the interaction, the scripting surface, the editor's side, the demos, each a paragraph a milestone can point at for the part it lands.

**§3. Milestones.** Open with: numbered and listed in execution order, M1 through M<n>, each run after the one above it is committed and released; the order's logic in a sentence; what each gives; "Fresh thread" means a new thread with the prompt as its first message. Then each milestone:

- Heading: `### M<n>. <what it lands> — <branch>` with ` — pipeline change (<why>)` where it is one, `(no project code; <the other repository>)` where it lands none, `(stretch)` or `(optional)` where it is.
- **Seams.** (or **Design.**, **Fields.**, **Where.**, as the milestone needs): the files and functions by name, the precedent's touched files, what is settled from a dependency's source and recorded in a module header, what is left out and why.
- **Reuse.** The existing functions and modules the milestone builds on.
- **Acceptance.** Unit: the tests by file, what each proves. Live: the named projects and pairs, each with its measurement, and the one difference the milestone must show. The changelog line the commit carries, with the compatibility word the project's rule asks for.
- **Model.** `<Model> <version>, <effort>, fresh thread (<why this level>)`. The levels, from the two plans: Sonnet 5.5 at medium for a pure rule with a call site or two, a registration, a script and a folder copy; Opus 5.5 at medium for a local change with a subtlety or two; Opus 5.5 at high for many lists or rows where a missed one silently breaks something, an editor's seams, a port; Fable 5.1 at high for a new kind through every seam, a new surface that must agree with another to the pixel, authoring across everything the plan built; xhigh, on Fable 5.1 or Opus 5.5, for a pipeline change: anything that sits ahead of every frame or every input, changes a lifecycle that recompiles or re-arms everything, or takes a global property away. State the reason on each, and say why high is enough where a pipeline change gets less. Name Fable 5.1 where the strongest model is needed; §0's handoff rule substitutes Opus 5.5 at the same effort where Fable is not available.
- **Prompt.** A fenced block, paste-ready and self-contained: `Read <plan path> §1 (rules, harness), §2 and §3 M<n>, then <the files to read first>.` then on which branch and under which worktree rule, what to build as M<n> specifies in a sentence or two that names the parts, the constraints that matter most (what not to touch, what the header or the commit must say), `Tests as M<n> lists.`, the live checks as M<n> lists with the projects named, the checks and the commit with its count, what to report (counts, numbers, what could not be done), and the closing line: for a pipeline milestone, `This is a pipeline milestone, so before the verdict put a section headed READ THIS EVIDENCE: three to five bullets naming the before/after pairs and numbers <name> should look at, each with the file path of its screenshots or sampled values, the project it came from, and what a wrong result would look like there.`; then always `End as §1 defines: a PLAN CORRECTIONS section, then the closing verdict line (CLEAR or ACTION NEEDED).` A milestone that ends ACTION NEEDED by design says so in its prompt and names the things that are the user's.
- **Commit.** The branch, how many content commits and which, and the release the user runs afterwards: the release skill by name, in the thread its rules ask for, with the version written in only where the release takes a number other than the skill's own bump, as step 6 says; `None` with the reason where the milestone commits nothing (another repository, no project code); the rebase or the user's action the release depends on.
- **Executioner.** Only under the milestones whose review runs at xhigh: "The message that hands over this prompt ends `Next turn: xhigh`; the review of this milestone runs at xhigh and ends `Next turn: high`" (or xhigh again where the next review is one too). Which reviews those are is the plan's judgment: every pipeline milestone's, and any milestone whose report judges many things at once, such as a demo of many scripted effects.

Order the milestones so that each stands on what is released before it: pipeline changes first, each proven to leave the existing projects identical; then additions in dependency order; a port before the removal it frees; an editor half after the player half it needs is released and rebased onto; assets and demo folders where nothing earlier needs them and where a new folder's effect on the test count is stated; demos and authoring last; stretch and optional work at the end with what runs without it. Number them in that order, top to bottom: the reader runs them by reading down the file.

**§4. Verification of the finished work.** Numbered: load, the walk through every behaviour on the harness with its read-backs, the user's device checks, performance as ratios, and a regression pass against the starting tip naming the projects that must be identical.

**§5. Considered and left out.** One list, each item with its reason in a clause.

**§6. Open risks.** What the stress test (step 8) left open, each numbered with what would settle it. Omit the section when there is none.

## 6. Versions and the release skill

Where the project keeps version commits, read from the release skill what it does given no version (the generic `/commit` increments the last number of the last version commit's) and how a version is passed (its argument hint). The plan's rule: a release is a plain `/<skill>` wherever that bump gives the number the release should carry, a line's first release included, so a release command never restates the bump. A version is written in, `/<skill> <version>`, only where the number differs from the bump: a jump, from the arguments or step 4, or a line with no version commit yet, whose first number the user gives in step 4; every release after it is plain again, bumping from what was entered, so numbers run in release order. Say in §1 which milestones release nothing. Where no release skill is installed, the Commit lines say how the project releases, or "commit on <branch>" alone.

## 7. Write and check

Write the file in sections, each with a marker for the next (`<!-- §3 follows -->`), so a cut in the output costs nothing; replace the markers as the sections land. Then check with grep, and fix what fails:

- no marker is left; the heading list reads §0 to §5 (§6 where it exists) with the milestones in order
- every milestone has Model, Prompt and Commit; the fence count is twice the prompt count; every prompt names the plan's path and its own section
- the version strings and release commands agree with §1's scheme; no milestone's number is a leftover label
- no reference to a section, milestone or file that no longer exists after a renumbering
